# 9-15 北斗频点映射专项（phone BDS C2I 偏差定位与默认映射 GREAT 对齐）

> 状态：已完成。结论：8-24「GPS+BDS 组合 V_rms 95 m」的根因是**简化器把 BDS B1I
> 观测码 `2I` 归入 GPS/GAL 的 L2 频点族**，导致简化后 BDS 观测整段被剔除/错配；
> 修复后 phone GPS+BDS 水平 RMSE 从 6.60 m 改善到 **3.31 m**，优于 GPS-only 的
> 4.33 m。BDS 并星由「暂停」改为「可用，剩余逐卫星常偏待建模」。

## 1. 背景与任务

8-24 记录：TC 的 zdres/DD 路径对手机 C2I 存在系统性偏差（GPS+BDS 组合
V_rms 95 m），暂停 BDS 待专项定位。本轮按指示开展独立专项：

1. 先做逐卫星残差 dump 定位 C2I 偏差来源，不直接并星；
2. 北斗信号处理参考 GREAT，默认频点映射尽量向 GREAT 靠拢；
3. phone 数据与默认处理冲突的部分，在 `phone/rtdtc.yaml` 显式配置适配。

## 2. 频点映射机制（修复前的事实梳理）

gipylib 存在三套编号，正交且极易混淆（详见 `skills/conf.md` 第 3.15 节）：

| 域 | 例子 | 作用 |
|---|---|---|
| **raw RINEX band digit** | 观测码第二字符：`C1C`→1、`C2I`→2、`C6I`→6 | RINEX 文件物理频点；`raw_band_priority` 的键 |
| **solver freq_ix** | `freq_table[6]=1.561098 GHz`（phone 的 B1I） | 解算频率表索引；与 band 无位置关系 |
| **normalized band** | `RAW_TO_NORMALIZED_BAND`：C 系统 `{1:0, 2:1, 6:4, 7:3}` | 简化器内部的频点序（第一/第二频点…） |

关键代码路径：`phone.25o` → `simplify_rinex(raw_band_priority)` → `rnx_decode.decode_obs`
（`raw_band_to_slot` 槽位映射，未知 band 硬报错 `unsupported_raw_band`）→
`zdres/selsat` → `RtdTcMeas._build_dd`（DD 行）。

GREAT 的 BDS 频带依据：`GREAT-MSF/src/LibGnut/gutils/gnss.cpp:78`
`m[BDS] = {BAND, BAND_2, BAND_7, BAND_6, ...}` 注释 `B1I B2I(BDS-2) B3I ...`，
即 **B1I=BAND_2（观测码 C2I）、B3I=BAND_6（观测码 C6I）**；GREAT campus01
单频基线实际选用 B3I（C6I）。

## 3. 发现与修复（按定位顺序）

### F1 RTD 模式测量 trace 未接线（诊断能力缺口）

`tc_integration._build_measurement_builder()` 只在 `mode=="rtk"` 时把
trace sink 传给量测 builder，且 `RtdTcMeas.__init__` 根本不接受
`trace_sink`；RTD 的 `build()` 也不创建 trace context。campus01 用 rtk
所以 trace 一直有效，phone 用 rtd 则拿到 0 字节 JSONL。

修复：`RtdTcMeas.__init__` 透传 `trace_sink/trace_callback`；
`_build_measurement_builder` 对 `rtk/rtd` 都传 sink；
`RtdTcMeas.build()` 入口 `_trace_begin`、成功/空历元路径 `_trace_finish`、
`_build_dd(..., trace_context=...)`。

### F2 `needs_simplification` 不感知 `raw_band_priority`（诊断链第二缺口）

phone.25o 在 GPS L1 之外声明了 L5；简化判定只看频点数/交织，判定"不需
简化"，而解码器槽位映射（默认 GPS [1,2]）不含 band 5 →
`unsupported_raw_band` 硬报错。修复：`needs_simplification` 增加声明
band 超出优先集的检查，`_prepare_rinex` 传入优先级。

### F3 简化器把 BDS B1I 归入 L2 频点族（★C2I 偏差专项根因）

`rinex_simplifier._FREQ_ORDER` 把观测码 `2I` 映射到 normalized 3
（GPS/GAL 的 L2/E5b 族），而 band 级权威表
`RAW_TO_NORMALIZED_BAND['C'][2] = 1`（B1I 属第一频点族）。
两者矛盾 → 简化器把手机 BDS 的 `C2I L2I D2I S2I` 整段当"非优先频点"
剔除：简化输出头里 **C 系统整个消失** → `candidate_sats['C']=[]` →
DD 行 27236 条全部 GPS、0 条 BDS。

这同时解释 8-24 的历史现象：当时无 `raw_band_priority` 概念，BDS 观测
按列位置错误落槽，产生"GPS+BDS V_rms 95 m"。

修复：`_FREQ_ORDER["2I"] = 1`（`6I/7I` 等其余 BDS 代码与 band 表本就
一致）。修复后简化输出保留完整 `C 4 C2I L2I D2I S2I` 段。

### F4 默认 BDS 频点映射与 GREAT 冲突

- 旧 `LEGACY_FREQ_BAND_METADATA["BDS"][6] = 1`（声称扩展表 B1I→band 1），
  而 GREAT 的 freq_ix 6 → B3I（C6I，band 6）——同一索引两种意图。
- 旧 `DEFAULT_RAW_BAND_PRIORITY["C"] = [1, 6]`（B1C+B3I）；B1C 仅 BDS-3
  且手机等大量接收机不存在。

修复（GREAT 对齐）：

- `LEGACY_FREQ_BAND_METADATA["BDS"] = {0: 2, 1: 7, 2: 5, 3: 7, 4: 6, 5: 7, 6: 6}`
  （0→B1I band 2；6→B3I band 6；`gnss.cpp:78` 为依据）；
- `DEFAULT_RAW_BAND_PRIORITY["C"] = [6, 2]`（B3I 优先，B1I 次之，与
  campus01 单频基线一致）。

影响面核查：所有启用 BDS 的在用配置中，campus01 两条链与 phone/rtdtc
均为显式 `raw_band_priority`，不受默认值影响；仅 `phone/rtd.yaml` 与
`phone/rtd_gps_bds_debug.yaml` 走默认（原本被 B1C 误映射所坏，属修复）。
`tests/test_sensor_raw_band_mapping.py` 的 legacy 期望同步更新（C: [2, 7]）。

### F5 phone 配置适配（数据特殊性，按指示落在配置里）

`phone/rtdtc.yaml`：

- `gnss_t: ["GPS", "BDS"]`（单频 `raw_band_priority: {GPS:[1], BDS:[2]}`）。
  **BDS 用 band 2 而非 6**：手机 rover 只有 B1I（C2I），基站 B1I/B3I 兼有，
  共同频点 = B1I。注意 `freq_ix0: {BDS: 6}` 保留（phone 频率表
  `freq_table[6]=1.561098 GHz` 即 B1I），两套编号正交；
- 开启 `tc.measurement_trace`（残差 dump 数据源）。

## 4. 逐卫星残差 dump 结果（GPS+BDS，全窗 91075 条 DD 行）

分析工具：`phone/plot/residual_dump.py`（逐 DD 行流式解析
`prefit_innovation/postfit_residual/system/target_prn/kind`，输出
`residual-summary.csv`、`residual-by-satellite.csv`、`residual-dump.png`）。

系统级 prefit（修复 F3 后）：

| system | kind | count | mean (m) | std (m) |
|---|---|---|---|---|
| GPS | code | 27482 | +0.49 | 7.22 |
| BDS | code | 63593 | +10.39（含巨野值） | 2377.7 |

逐卫星拆解（|prefit|>50 m 计为野值）：

| 类别 | 卫星 | n | mean (m) | std (m) | 定性 |
|---|---|---|---|---|---|
| GEO | C01 | 3838 | +157（**野值最大 +599600**，仅 3 行） | 9677 | 位置计算故障历元（0.04% 行） |
| GEO | 其余 | 14351 | **+0.34** | 5.50 | 正常，与 GPS 同量级 |
| IGSO | C06/C08/C09 | ~14440 | **+0.93 ~ +1.71** | ~4.4 | 系统性常偏 |
| MEO | C41 | 1604 | **+13.35** | 14.19 | 持续常偏 |
| MEO | C40 | 10 | +234 | 49 | 异常历元（样本少） |
| MEO | C20/C23/C32/C38/C39/C59/C60 | ~23000 | −0.77 ~ +0.68 | 4.1–5.9 | 正常 |
| MEO | C19 | 414 | +2.04 | 10.21 | 样本少 |

结论：**不存在统一 ISB 级常偏**（统一偏差会被接收机钟差吸收）；偏差是
**逐卫星伪距系统偏差**（BDS B1I satellite-dependent code bias，文献已知
现象，BDS-2/3 各星硬件延迟差异数米量级）叠加两个孤立故障源
（C01 GEO 星历故障历元、C41 持续 +13 m）。

## 6. 剩余问题与后续

1. **C41（+13.4 m）与 C01 GEO 故障历元**仍是次级污染源。短期可在
   `phone/rtdtc.yaml` 用 `excsats: ["C40", "C41"]` 验证增益；更稳的做法是
   在 `_build_dd` 前加逐 DD 行 prefit gate（绝对门限 + 卫星级统计），替代
   现在只能事后回滚的 `pos_jump_reject`（本轮观测到一次 50.92 m 跳变回滚）。
2. 中期：为 BDS B1I 引入逐卫星伪距偏差状态（GREAT/文献的
   satellite-dependent bias 模型），IGSO/MEO 的 +1~1.7 m 常偏可被吸收。
3. `phone/rtd.yaml` / `phone/rtd_gps_bds_debug.yaml` 走新默认（B3I 优先），
   但手机 rover 无 B3I——这两份配置若要使用，需按 phone/rtdtc.yaml 显式
   `raw_band_priority: {GPS:[1], BDS:[2]}`。
4. 运行日志中 `TC pos_jump_reject (t=1756716833): jump=50.92 m` 与 C01 GEO
   野值时间对齐，印证保护逻辑有效但属最后防线。
