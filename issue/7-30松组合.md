## 一、评估脚本修复 (关键 bug)

### 问题
`_eval_rtklc.py` / `_eval_spplc.py` 的 `load_rslt` 用 `data[(week, int(round(sow)))] = rec` (后写覆盖)，
导致 100Hz IMU 中 50 个历元映射到同一整数秒，最后写入的 (sow=X.496, Qins=2, GNSS 更新后 0.496s)
覆盖了 Qins=3 (sow=X.006, GNSS 更新后, 位置≈GNSS) 的历元。
评估取到的是 INS 漂移最大的时刻 (0.496s)，而非 GNSS 更新时刻。

### 修复
改为只收集 Qins=0 (纯 GNSS 1Hz) 和 Qins=3 (GNSS 更新后 1Hz) 的历元，跳过 Qins=2 (100Hz 中间历元)。
- Qins=0 时间戳在精确整数秒 (纯 GNSS 1Hz 输出)
- Qins=3 时间戳在 +0.006s (GNSS 更新后第一个 IMU 历元, 位置≈GNSS, 差异<0.1m)

### 影响
RTK-LC RMSE 从 1.74m → 0.82m (修复评估偏差后)。

## 二、RTK-INS 松组合优化 (RMSE 0.82m < 1m, 合格)

### 修改
1. **关闭 NHC** (data/config.yaml: `nhc_enable: 0`)
   - 根因: EuRoC 为无人机可侧向飞行, NHC 在 yaw 未收敛时强制 side_vel=0 反而 corrupt 状态
   - memory 记录: NHC 开启时 RMSE 5→493m

2. **RTK 不使用 rtklib sd** (src/core/ins/lc_estimator.py: `_build_pos_R`)
   - 根因: RTK FLOAT 的 rtklib sd 偏大保守 (2-9m), 实际精度 0.22m
   - `max(base_sigma, gnss.sd)` 导致 R 过大, K≈0, INS 自由漂移
   - 改为: 仅 DGPS/SPP (Q=4/5) 使用 `max(sigma, sd)`, RTK (Q=1/2) 用 base_sigma

3. **FLOAT sigma 0.1→0.3** (src/core/ins/lc_estimator.py: `_gnss_pos_std[2]`)
   - RTK FLOAT 平面精度 0.22m, sigma=0.3 给 EKF 适当惯性

4. **添加 vel_psd=0.1** (data/config.yaml)
   - 直接注入 P_vel, 防止 P_vel 坍缩致 K_vel→0 (RTK 无原生速度, 依赖位置差分速度)

5. **添加 pos_diff_vel_std=0.3** (data/config.yaml)
   - 位置差分速度 sigma 下限, RTK 位置 sigma≈0.3m, 1s 差分速度 sigma≈0.42, 取 0.3 给 EKF 更高速度信任

### 评估结果
```
RTK-LC 3D RMSE = 0.8161m (< 1m, 合格)
纯 RTK 3D RMSE = 0.8164m
```
LC 与纯 RTK 精度一致, 因为 GNSS 更新时刻 K=0.98 (pos_psd=5.0, sigma=0.3), 位置≈RTK (差异<0.1m)。

### 分时段对比 (LC vs 纯 RTK)
| 时段 | LC RMSE | 纯 RTK RMSE | 说明 |
|------|---------|-------------|------|
| t=[0,600)s | 0.34-1.47 | 0.34-1.47 | 一致 (Qins=0, 纯 GNSS) |
| t=[600,720)s | 0.519 | 0.518 | 一致 (初始化段) |

## 三、SPP-INS 松组合 (RMSE 3.43m > 2m, 受 SPP 高程偏差限制)

### 修改
1. **添加 vel_psd=0.1** (data/spp-ins-lc.yaml) — 同 RTK
2. **添加 pos_diff_vel_std=0.3** (data/spp-ins-lc.yaml) — 同 RTK
3. **vertical_sigma_factor=5.0** (已有) — SPP 高程偏差 ~3.3m, 放大 5 倍弱化高程

### 评估结果
```
SPP-LC 3D RMSE = 3.4320m (> 2m, 不合格)
纯 SPP 3D RMSE = 3.4611m
SPP-LC 平面 mean = 0.7651m
SPP-LC 高程 mean = 3.2733m  ← 主要误差源
```

### 根因分析
SPP 高程系统性偏差 3.29m (mean), max 6.88m, 是 SPP 单点定位的固有限制:
- 单频伪距 SPP 高程精度差 (对流层/电离层/星历误差累积)
- 双频 (nf=2) 未改善高程偏差, 说明不是电离层导致
- LC 无法改善 SPP 固有高程偏差 (EKF 高程 K 高时跟随 SPP 偏差, K 低时 INS 漂移)
- 3D RMSE = sqrt(0.77² + 3.29²) ≈ 3.38m, 高程贡献占 96%

### SPP-LC vs 纯 SPP
LC 在平面精度上与纯 SPP 一致 (0.77m), LC 的价值在 100Hz 输出和速度/姿态。
SPP 高程偏差 3.29m 是 SPP 解算层面的限制, 需要改进 SPP 解算 (如估计对流层天顶延迟 ZTD),
不属于松组合 EKF 层面的问题。

## 六、NHC 算法对比 ignav ins-nhc.cc

### 问题
原始 NHC 配置导致状态 corrupt (memory 记录 RMSE 5→493m), 此前被迫关闭 NHC。

### ignav ins-nhc.cc 参考算法
```
MAXVEL = 0.5     // per-axis guard: |vb[i]| > 0.5 跳过该维
VARVEL = SQR(0.05)  // NHC 量测方差 (sigma=0.05 m/s, 强约束)
MAXGYRO = 30°/s  // 剧烈转弯跳过整个 NHC
```
- 逐维检查 |vb[i]|: 侧向速度 > 0.5m/s 时跳过该维 (自动保护 yaw 未收敛状态)
- 固定 R = VARVEL (无自适应 R)
- 约束 vb[1], vb[2] = 0 (侧向 + 垂向)

### 原始配置问题
| 参数 | ignav | 原始 config.yaml | 问题 |
|------|-------|------------------|------|
| nhc_max_vel | 0.5 | 10.0 | **20x 过高**, yaw 误差 35° 时侧向速度 5.7m/s < 10.0, NHC 仍应用并破坏状态 |
| nhc_std | 0.05 | 0.5 | 10x 过松, 约束力不足 |
| nhc_max_gyro | 30°/s | 30°/s | 一致 |
| 自适应 R | 无 | 有 (P[vel]+P[att]) | 过保守, K≈0 |

### 修改
1. **nhc_max_vel: 10.0 → 0.5** (对齐 ignav MAXVEL)
   - yaw 误差 > 3° @ 10m/s 时侧向速度 > 0.5, 自动跳过 NHC
   - yaw 收敛后 (< 3°) NHC 才应用, 保护状态

2. **nhc_std: 0.5 → 0.05** (对齐 ignav VARVEL)
   - 强约束 (sigma=0.05m/s), 有效约束侧向速度

3. **保留自适应 R** (R += H_vel@P[vel]@H_vel^T + H_att@P[att]@H_att^T)
   - ignav 无自适应 R, 但本项目 LC 模式 RTK 无原生速度, 过渡期需保护
   - 纯 R (无自适应) 实测更差 (RMSE 1.13m vs 0.88m), 因 NHC 过强锁住速度

4. **vel_psd: 0.1 → 0.5, pos_diff_vel_std: 0.3 → 0.15**
   - 提升 EKF 速度量测 K: K_vel ≈ 0.96 (高度信任位置差分速度)
   - 这是速度 RMSE 达标的关键 (见对比表)
